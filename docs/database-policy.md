# Local database policy
- One SQLite/Drift database in private Application Support/bubka-data; no cloud, no deletion on error. The directory is excluded from iOS backup before opening; Android backups and device-transfer paths are excluded. Runtime verification on physical devices is deferred.
- Schema v1: technical diagnostics and module availability only. The composition root registers repositories; core does not depend on feature implementations.
- Future business entities use stable opaque IDs, never registration plates. Money is integer euro cents; odometer uses integer kilometres (or integer metres if finer resolution is required); quantities use explicitly documented scaled integers such as millilitres. Calendar dates are ISO 8601 YYYY-MM-DD; timestamps are UTC instants and rendered in the user's time zone.
- Use `dart run build_runner build`, then `dart run drift_dev make-migrations`. Commit generated files and schema snapshots. On real schema changes add explicit incremental migration steps, run migration verification from every supported version, and test record retention. Never reset production data or add fake production schema versions.
- Before a future risky migration, quiesce writers and use a SQLite-supported consistent snapshot (e.g. online backup API or VACUUM INTO on a controlled connection). Do not copy a live main file without accounting for WAL. Verify integrity and readability of the snapshot, preserve the original on error, show a local recovery message. An actual user-facing restore feature is outside phase 02.

## Phase 03 snapshot implementation (pending CI)
SnapshotService uses SQLite VACUUM INTO through the existing Drift connection outside transactions. SQLite provides a consistent snapshot, including committed WAL data; callers must await completion and must not call from inside a transaction. One service instance serializes snapshot requests by rejecting overlapping calls. Staging and final copy are under the excluded private data directory; integrity and foreign key checks run before atomic replacement of the last successful snapshot. Never restore while the database is open. For future manual recovery, close all connections, preserve the damaged original and its WAL/SHM separately, validate the snapshot, then use a controlled offline restore. No automatic deletion or restore is implemented.

Phase 03 adds a SchemaVerifier test against the exported v1 schema. The production schema remains 1. The notification plan is separate private JSON under the same backup-excluded directory; it stores local calendar wall times, not UTC instants. No vehicle data is sent to a server.
